Deploy Models

Before a model can be used in production, it often needs to be packaged, optimized, and prepared for its target runtime environment. This stage focuses on converting models into supported deployment formats, applying platform-specific optimizations, and preparing them for execution on IBM LinuxONE.

IBM LinuxONE supports multiple deployment paths based on the model type and target inference environment. Models developed with open-source and commercial frameworks — whether trained on LinuxONE or in a hybrid cloud environment — can be deployed using the same set of IBM LinuxONE deployment and serving technologies.

What happens at this stage?

Convert to a portable format

Export your trained model to ONNX (deep learning) or PMML (traditional ML) — standard interchange formats supported by IBM LinuxONE deployment tools. If you are running IBM Z Accelerated for TensorFlow or IBM Z Accelerated for PyTorch natively, you can deploy directly without ONNX conversion.

Optimize for IBM LinuxONE hardware

For deep learning models and encoder LLMs targeting the Telum II on-chip AI accelerator, compile with the IBM Z Deep Learning Compiler (zDLC) after ONNX conversion. For LLMs served on Spyre via Red Hat AI Inference Server or Red Hat OpenShift AI, no ONNX conversion or compilation is required — models are served natively. Traditional ML models do not require this step.

Move to production

Deploy your model to a production runtime on IBM LinuxONE — co-located with the enterprise data and Linux workloads it needs to score, with no data movement required.

Configure scoring endpoints

Set up the model to receive inference requests via REST API or gRPC serving endpoint, integrated with your Linux applications and containerized services on IBM LinuxONE.

Who is this stage for?

Optimization and deployment are typically owned by ML Engineers and IT Architects. The ML Engineer handles model conversion, compilation, and the deployment artifact. The IT Architect owns the infrastructure decisions — serving topology, containerization strategy, and integration with business applications on IBM LinuxONE. Data Scientists are stakeholders who validate that the deployed model performs as expected.

Where to Start

Your path is determined by two things: your model type and your target accelerator. The three subsections below map to those two dimensions.

Deploying Traditional Machine Learning Models

Traditional ML models (classification, regression, recommendation, forecasting) are deployed via PMML and will either leverage the Telum II on-chip AI accelerator (e.g., gradient boosting and random forest models) or run on native CPU (e.g., linear regression and logistic regression). Not all traditional ML models use the on-chip AI accelerator.

You have a model trained with IBM Z Accelerated for Snap ML, scikit-learn, XGBoost, or another traditional ML framework and need to move it to production on IBM LinuxONE.

→ Export to PMML and deploy via the AI Toolkit for IBM Z and IBM LinuxONE scoring services or Red Hat OpenShift AI. PMML provides a portable format that does not require the original training framework at inference time, and is supported by IBM LinuxONE serving tools.

Common approach: Train with IBM Z Accelerated for Snap ML or scikit-learn → Export to PMML → Deploy and score via AI Toolkit for IBM Z and IBM LinuxONE or Red Hat OpenShift AI on IBM LinuxONE.

Note: IBM Z Accelerated for Snap ML is primarily a training technology. Deployment begins after exporting the PMML model.

You want model deployment, lifecycle management, monitoring, and scoring endpoints managed through a unified platform on IBM LinuxONE.

→ Use Red Hat OpenShift AI or watsonx.ai on IBM LinuxONE. Red Hat OpenShift AI provides KServe-based model serving, deployment pipelines, and monitoring within a Kubernetes-native environment. watsonx.ai (via IBM Software Hub) provides a full ML deployment and lifecycle management environment. Both run on IBM LinuxONE and expose REST scoring endpoints for integration with your Linux applications.

Common approach: Train model → Export to PMML or ONNX → Import into Red Hat OpenShift AI or watsonx.ai → Deploy as a REST scoring endpoint on IBM LinuxONE.

Deploying Deep Learning Models and Encoder LLMs (Telum II On-Chip Accelerator)

Deep learning models and encoder LLMs share the same deployment path on IBM LinuxONE to enable Telum II on-chip AI acceleration: convert to ONNX, compile with the IBM Z Deep Learning Compiler (zDLC), and deploy via a serving platform. Unlike traditional ML models, these heavier-weight models should always target the Telum II on-chip AI accelerator. Encoder LLMs can also choose the Spyre path — see the next subsection.

You have a neural network trained with IBM Z Accelerated for TensorFlow, IBM Z Accelerated for PyTorch, or any other framework — including models trained externally with Keras or Hugging Face — and want to deploy it on the Telum on-chip AI accelerator.

→ Convert to ONNX, then compile with the IBM Z Deep Learning Compiler (zDLC). zDLC optimizes the ONNX model for IBM LinuxONE hardware, generating a deployment artifact that leverages Telum II AI acceleration automatically. The zDLC supports C++, Java, and Python APIs and produces shared library files embeddable in applications independently of the original framework.

Common approach: Export model to ONNX → Compile with zDLC → Deploy via IBM Z Accelerated for Triton Inference Server or Red Hat OpenShift AI on IBM LinuxONE.

Your model was built with IBM Z Accelerated for TensorFlow and you want to skip ONNX conversion by deploying directly with IBM Z Accelerated Serving for TensorFlow.

→ Export as a TensorFlow SavedModel and deploy with IBM Z Accelerated Serving for TensorFlow. This avoids the ONNX conversion step while still leveraging Telum hardware acceleration.

Common approach: Train with IBM Z Accelerated for TensorFlow → Export SavedModel → Deploy to IBM Z Accelerated Serving for TensorFlow.

Note: The ONNX → zDLC path is also valid for IBM Z Accelerated for TensorFlow models and gives access to IBM Z Accelerated for Triton Inference Server or Red Hat OpenShift AI as serving platforms.

You need to serve multiple model types from a shared inference platform, or your team works in a containerized OpenShift environment.

→ Use IBM Z Accelerated for Triton Inference Server, optionally managed through Red Hat OpenShift AI. IBM Z Accelerated for Triton Inference Server supports TensorFlow, PyTorch, ONNX, and zDLC-compiled models from a single serving runtime.

Common approach: Convert model to ONNX and compile with zDLC → Deploy to IBM Z Accelerated for Triton Inference Server → Optionally manage deployment pipelines and monitoring through Red Hat OpenShift AI.

You have an encoder large language model (e.g., BERT-style) and want to run it on the Telum on-chip AI accelerator rather than Spyre.

→ Convert the encoder LLM to ONNX and follow the same deep learning path: compile with zDLC and deploy via IBM Z Accelerated for Triton Inference Server or Red Hat OpenShift AI on IBM LinuxONE.

Common approach: Export encoder LLM to ONNX → Compile with zDLC → Deploy via IBM Z Accelerated for Triton Inference Server or Red Hat OpenShift AI on IBM LinuxONE.

Note: Encoder LLMs can also be served on Spyre — see the next subsection. As a general guide: models with approximately 300 million parameters or fewer are a good fit for the Telum II on-chip AI accelerator; models up to approximately 30 billion parameters can run on Spyre; models larger than that are not suited for IBM LinuxONE. The right choice also depends on your application SLAs and hardware availability.

Deploying Large Language Models on Spyre

Decoder LLMs always use Spyre. Encoder LLMs may also choose Spyre over the Telum on-chip AI accelerator depending on Application SLAs, model size, and hardware availability. The tools in this subsection are specific to Spyre-accelerated LLM workloads.

You are deploying a decoder LLM (e.g., Llama, Granite) or an encoder LLM on Spyre and want a dedicated inference server without the full Red Hat OpenShift AI platform. No ONNX conversion is required — LLMs are served natively.

→ Use Red Hat AI Inference Server. This is the recommended path for LLM inference on Spyre without requiring the full Red Hat OpenShift AI platform. It is vLLM-based, purpose-built for large model inference, and supports Granite, Llama, Qwen, DeepSeek, Gemma, Mistral, and other models — no ONNX conversion required. Not used for traditional ML or deep learning models on the Telum II accelerator.

Common approach: Source or fine-tune an LLM → Deploy natively via Red Hat AI Inference Server with Spyre acceleration on IBM LinuxONE.

You need MLOps pipeline management, model catalogs, and monitoring around your LLM deployment, or you want a single platform that covers both Telum and Spyre workloads. No ONNX conversion is required for LLMs — they are served natively through the Red Hat AI Inference Server runtime embedded in OpenShift AI.

→ Use Red Hat OpenShift AI. Both Red Hat AI Inference Server and Red Hat OpenShift AI are valid paths for LLM inference on Spyre — no ONNX conversion required for either. Choose OpenShift AI when you need the broader platform: MLOps pipelines, model governance, and unified management across Telum II and Spyre workloads on IBM LinuxONE.

Common approach: Deploy LLMs through OpenShift AI using the Red Hat AI Inference Server runtime for Spyre workloads, or IBM Z Accelerated for Triton Inference Server for Telum II workloads — all managed from a single MLOps platform on IBM LinuxONE.

You have a hybrid deployment that spans IBM LinuxONE and other platforms (cloud, GPU clusters), and you need intelligent routing of LLM inference requests to the most optimal platform.

→ Use AI Optimizer for IBM LinuxONE. AI Optimizer is a complete software appliance — delivered as a single LPAR image — that boots a fully optimized inferencing stack ready in under 2 hours. It acts as a policy-driven gateway routing inference requests to the most optimal endpoint (Spyre, Telum II, or external) based on tagging and model grouping. It integrates Red Hat AI Inference Server and includes real-time monitoring via Prometheus & Grafana.

Common approach: Deploy AI Optimizer as the inference gateway on IBM LinuxONE → Register on-platform and external LLMs → Route inference requests to Spyre via the embedded Red Hat AI Inference Server or to an external environment based on configured policy.
