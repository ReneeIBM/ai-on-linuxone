Serve Model

Serving is the stage where a deployed model is made available for production use. On IBM LinuxONE, as soon as a model is deployed a scoring endpoint is created — serving and deploying are effectively the same step. This stage focuses on invoking that endpoint from your applications and managing the model in production over time.

The invocation method depends on your runtime: models deployed in IBM Z Accelerated for Triton Inference Server, IBM Z Accelerated Serving for TensorFlow, or Red Hat AI Inference Server are called via REST or gRPC. Invocation happens directly on IBM LinuxONE, close to enterprise data, reducing latency and enabling AI to be embedded into your Linux applications and containerized services.

What happens at this stage?

Integrate the model into your application

The scoring endpoint is created at deploy time — this stage is about wiring it into your business application via REST API or gRPC from your Linux workloads and containerized services on IBM LinuxONE.

Handle production traffic

Configure dynamic batching, concurrency, and throughput settings to handle inference requests at high throughput and low latency while meeting SLA requirements on IBM LinuxONE.

Manage model versions

Support model versioning and controlled updates, allowing new model versions to be swapped in, tested, and rolled back with minimal disruption to production workloads.

Infuse AI into applications

Embed inference directly into Linux applications and microservices co-located with enterprise data on IBM LinuxONE — eliminating data movement and minimizing latency for real-time transactional AI.

Who is this stage for?

Serving is typically owned by ML Engineers and Application Architects, with Data Scientists as stakeholders validating that the serving layer produces correct outputs. Line of Business and IT Architects set the SLA and throughput requirements the serving layer should meet.

Where to Start

Your invocation method follows from the runtime your model was deployed to. The accordions below map to each runtime available on IBM LinuxONE. Encoder LLMs can run on either Telum (Triton) or Spyre (Red Hat AI Inference Server) — see the relevant accordion for each.

Invoking Models on Telum (Traditional ML, Deep Learning, and Encoder LLMs)

Models deployed through Telum-based runtimes on IBM LinuxONE are invoked via REST or gRPC endpoints from your Linux applications and containerized services. The runtime you deployed to determines how you call the endpoint.

Your model — traditional ML (PMML or ONNX), deep learning (zDLC-compiled ONNX), or encoder LLM — is deployed in IBM Z Accelerated for Triton Inference Server on IBM LinuxONE.

→ Invoke via gRPC or REST. IBM Z Accelerated for Triton Inference Server exposes both gRPC and HTTP/REST endpoints. Call the endpoint directly from your Linux application or containerized service co-located on IBM LinuxONE. Supports concurrent model execution and dynamic batching to meet strict SLAs.

Common approach: Send inference requests to the Triton gRPC or REST endpoint from your Linux application on IBM LinuxONE.

Your TensorFlow SavedModel is deployed in IBM Z Accelerated Serving for TensorFlow on IBM LinuxONE.

→ Invoke via HTTP REST or gRPC. IBM Z Accelerated Serving for TensorFlow exposes HTTP REST and gRPC interfaces. Call the endpoint directly from your application on IBM LinuxONE, leveraging Telum on-chip acceleration for each inference request.

Common approach: Send inference requests to the IBM Z Accelerated Serving for TensorFlow REST or gRPC endpoint from your application on IBM LinuxONE.

Your model is deployed and managed through Red Hat OpenShift AI on IBM LinuxONE — covering Telum and Spyre workloads across multiple teams.

→ Invoke via REST or gRPC through the KServe endpoint. Red Hat OpenShift AI exposes model endpoints via KServe — call the REST or gRPC endpoint from your application on IBM LinuxONE. Includes monitoring, alerting, and scaling controls around the serving layer.

Common approach: Send inference requests to the KServe REST or gRPC endpoint managed by Red Hat OpenShift AI from your Linux application on IBM LinuxONE.

Invoking Large Language Models on Spyre

Decoder LLMs always use the Spyre accelerator. Encoder LLMs may also choose Spyre over Telum depending on application SLAs and hardware availability. Applications invoke Spyre-accelerated LLMs via an OpenAI-compatible REST API — no ONNX conversion is required.

Your LLM is deployed on Spyre via Red Hat AI Inference Server on IBM LinuxONE.

→ Invoke via OpenAI-compatible REST API. Red Hat AI Inference Server exposes an OpenAI-compatible REST API. Call the endpoint from your application using standard OpenAI client libraries or any HTTP client. Supports Granite, Llama, and other models on IBM LinuxONE Spyre.

Common approach: Send inference requests to the Red Hat AI Inference Server REST endpoint from your application on IBM LinuxONE.

Your LLM is deployed through Red Hat OpenShift AI on IBM LinuxONE, with MLOps pipeline management, monitoring, and governance.

→ Invoke via REST through the OpenShift AI model endpoint. Red Hat OpenShift AI manages the Red Hat AI Inference Server runtime for Spyre workloads — invoke via the same OpenAI-compatible REST API, with monitoring, alerting, and scaling managed by the platform.

Common approach: Send inference requests to the OpenShift AI model endpoint from your application on IBM LinuxONE.

You have a hybrid environment spanning IBM LinuxONE and other platforms (cloud, GPU clusters) and need intelligent routing of LLM inference requests to the most optimal endpoint.

→ Invoke via the AI Optimizer gateway REST endpoint. AI Optimizer for IBM Z and LinuxONE acts as a policy-driven inference gateway — send inference requests to the gateway, which routes them to on-platform endpoints (Spyre or Telum) or external environments. Integrates with Red Hat AI Inference Server for Spyre workloads.

Common approach: Send inference requests to the AI Optimizer gateway endpoint on IBM LinuxONE — requests are routed to Spyre, Telum, or an external environment based on configured policy.
